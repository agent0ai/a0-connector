# Browser Bridge payload archive profile v1

Status: bounded source implementation; production release activation remains unavailable.

The signed release catalog continues to authenticate the immutable payload archive, not a raw executable. Stable v1 payload artifacts use one `.tar.gz` format on macOS, Windows, and Linux. Delivery wrappers, catalogs, signatures, checksums, SBOMs, notices, and attestations remain separate release artifacts.

Catalog version and payload archive version are independent. Catalog v1 still requires all nine delivery entries. Catalog v2 adds an authenticated, nonempty `platforms` list in strict ASCII lexical order (`linux`, `macos`, `windows`), and requires exactly the union of complete declared groups: macOS universal2 installer/payload, Windows x86_64 and arm64 installer/payload pairs, and Linux any bootstrap plus x86_64/aarch64 payloads. A Mac-only v2 catalog needs just its two genuine entries; omitted platforms cannot be selected. The payload archive format and every signature, digest, provenance, platform verification and runtime admission check remain unchanged. No incomplete group or placeholder for a future target is accepted as coverage.

## Exact archive profile

- The catalog entry has `kind: "payload"`, a supported platform/architecture pair, a non-empty `.tar.gz` name, and the exact compressed byte size and lowercase SHA-256.
- The gzip stream contains exactly one member. Its decoded tar stream is bounded to the lesser of 512 MiB plus tar overhead and a 64:1 expansion limit, with a 1 MiB minimum allowance for small valid fixtures.
- The tar contains exactly one USTAR regular-file entry at the root: `a0-browser-bridge` on macOS/Linux or `a0-browser-bridge.exe` on Windows. The entry is non-empty, at most 512 MiB, and carries readable/executable mode bits.
- Symlinks, hardlinks, devices, directories, traversal, prefixes, PAX/GNU extension entries, duplicate entries, notices, non-zero padding, more than 64 terminal zero blocks, trailing data, and concatenated gzip members are rejected.
- Extraction writes to a generated `0700` child and a generated `0600` file, then seals the file to `0500` and verifies its metadata. No archive path selects a filesystem destination.

The decoder hashes the same retained archive handle while it supplies compressed bytes to gzip. It checks the archive identity before and after the stream, the catalog size/digest, gzip integrity, tar structure, extracted byte count, and derived executable SHA-256. `VerifiedExecutablePayload` retains the exact archive and executable handles plus their identities and deletes only its generated staging inode/directory on drop.

## Candidate composition and remaining gates

Archive extraction is not an install candidate and does not execute the result. The crate-private `release_candidate.rs` composer now consumes the exact catalog and derived proof, checks their equality and current target, then invokes independent signature, provenance, embedded platform/version/contract, and offline self-test verifiers in that order. Both archive and executable are rehashed and rewound between phases. A failure stops subsequent phases; in particular, an unverified binary is never self-tested. The produced transaction retains the derivation proof and its generated staging cleanup owner. Installed executable digests remain distinct from compressed catalog artifact digests.

The concrete Linux self-test runner executes the retained inherited descriptor through `/proc/self/fd` with fixed `self-test --json` arguments, a cleared environment (only resolved HOME and C locale), null stdin/stderr, no shell/PATH lookup, an eight-second deadline, and a 2,048-byte output limit. A successful exit alone is insufficient: the composer requires the exact versioned nine-field report with real install readiness. This runner is only for the reviewed network-free self-test after the prior verification gates; it is not a general execution API or a networking sandbox. Its Linux-only smoke test still requires a Linux native test environment.

Darwin's public Security.framework and exec APIs are path-based. The macOS adapter now holds a create-only exclusive verification lease for the generated private pathname, checks current-user ownership/private parent chain and no symlinks/hardlinks, and rehashes the retained inode before/after each bounded system-tool or metadata/self-test execution. It uses a compiled exact Developer ID Application team/identifier requirement, all-architecture signature checks, hardened runtime and secure timestamps on both slices, and a positive notarized Developer ID assessment. A bounded Mach-O parser validates the embedded `__TEXT,__a0_release` identity in both Intel and Apple Silicon slices before the executable metadata command and self-test. No caller pathname is accepted; no installed state is changed during verification. This narrow platform exception does not claim protection against an already compromised same-UID process.

The concrete local-build provenance verifier accepts only exact bounded ASCII/JCS statements with detached Ed25519 signatures and separately compiled builder roots. It binds the catalog, archive, executable, target, source repository/commit/tree digest, recipe and Rust toolchain. GitHub Actions is optional; unsigned local logs/receipts are not provenance. Native macOS install/update now acquires compiled immutable catalog/provenance URLs, downloads the authenticated payload into private generated staging, composes every verification gate and invokes the transaction. The owner-supplied CWS draft origin, Developer ID metadata and genuine independent publisher/builder Ed25519 public roots are provisioned. Versioned direct-200 URLs use an update/delete-protected release tag; final downloads must still authenticate successfully, and final platform, installed-state and Core runtime evidence remain mandatory. Local-development builds cannot invoke stable composition despite these production roots.

Native release source pins signer roots and version-specific URLs, not the final hash of itself or its containing catalog. The latter would be circular. A separately built CLI may pin final companion bytes. The verified candidate retains exact signed catalog and local derivation statement bytes/signatures; installation publishes these four bounded private sidecars atomically with the executable. Native status verifies the retained signatures and measured executable digest against the signed archive-to-executable derivation, never an unsigned install-state assertion. Same-version reuse requires exact evidence readback. Detached statements can be signed after the executable and catalog are complete without rebuilding that executable.

Windows extraction now uses the dedicated private-DACL staging adapter with protected current-user/SYSTEM ACL readback, reparse/hardlink rejection, sealed retained read handles denying write/delete sharing and exact identity-checked cleanup. This is staging proof only: Authenticode/PE candidate verification and HKCU installation remain unavailable, and the Windows ACL/sealing acceptance test has not run on Windows. Unix mode checks are not claimed as Windows privacy.
